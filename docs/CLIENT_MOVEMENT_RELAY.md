2026-10-09 이동 송수신량과 서버 행동 대기열 계측을 추가했다. 집계 기준과 반복 확인 방법은 [MOVEMENT_METRICS.md](MOVEMENT_METRICS.md), 금일 결과와 스크럼·커밋 묶음은 [WORK_REPORT_2026-10-09.md](WORK_REPORT_2026-10-09.md)를 참고한다. 아래 2026-10-08 결과는 당시 실행 기록이다.

발판 맵 100000000의 이동 계산을 클라이언트로 옮겼다. 서버 Map tick은 행동 묶음의 송신 시각만 관리하며 이동·중력·충돌·착지를 계산하지 않는다. 자유 이동 맵 100000001의 기존 좌표 요청은 이번 변경 범위에 포함하지 않는다.

## 점프 상태 전이

1. 본인 클라이언트는 지상에서 새 Space 눌림을 받으면 즉시 점프하고 jumpId를 증가시킨다. 공중의 눌림은 예약하지 않으며, Space를 계속 누른 상태로 착지해도 자동 재점프하지 않는다.
2. Jump 행동에는 동작 번호, 발생한 클라이언트 tick, 점프 직후 위치·속도·방향을 넣는다. 서버는 해당 캐릭터를 공중 상태로 잠그고 같은 맵의 클라이언트들에게 중계한다.
3. 상대 클라이언트는 동일한 PlatformSimulation으로 점프·이동을 재현한다. 계산 상태와 화면을 분리하고 화면 위치에는 LERP를 적용한다.
4. 본인이 착지를 계산하면 동일한 jumpId의 Land를 보낸다. 서버는 이 보고를 받을 때만 점프 잠금을 해제한다. 공중에서 보낸 Grounded 체크포인트나 다른 jumpId의 착지는 잠금을 해제하지 않는다.
5. 착지 후에도 이전 jumpId의 Jump는 다시 실행되지 않는다. 새 점프에는 더 큰 jumpId가 필요하다. 맵 재입장 generation이 바뀌면 이전 맵의 행동은 무효다.

발판 끝에서 떨어지는 Fall도 공중 잠금을 사용한다. 낙하 복귀는 본인 클라이언트가 Respawn을 보고하고 서버가 시작 좌표·상태를 저장한다. 상대 화면은 이 경우 즉시 위치를 맞춘다.

## 전송 상한

- 클라이언트는 최소 200ms 간격으로 최대 32개 행동을 한 메시지에 넣는다. 이동 변경·Jump·Land·Fall·Respawn·Checkpoint가 같은 예산을 공유한다.
- 변경이 없으면 약 1초마다 상태 확인을 보낸다. 정지/직선 유지 중에 초당 5회를 채우지 않는다.
- 서버는 수신자별로 여러 캐릭터의 행동을 함께 묶어 최소 200ms 간격으로 한 메시지를 보낸다. 최대 54개 레코드, 전체 4,096바이트 이하이며 남은 행동은 다음 송신 구간에 보낸다.
- 서버가 밀린 tick을 따라잡아도 실제 송신 간격을 지키도록 현재 steady_clock 시각을 사용한다.
- 따라서 정상 런타임 발판 이동의 게임 메시지는 클라이언트 송신/서버의 수신자별 중계 각각 초당 5회 이하이다. 초기 지형·입장 상태, 자유 이동, 채팅, TCP/IP ACK·재전송은 이 상한에 포함하지 않는다.
- 전송 가능 시각까지 입력은 최대 약 200ms 기다릴 수 있고, 서버 중계 대기와 네트워크 지연은 별도로 더해진다. 본인 캐릭터는 이 대기를 적용하지 않는다.

클라이언트 행동 대기열은 128개, 수신자별 서버 대기열은 256개로 제한한다. 큰 맵/높은 행동 밀도에서 무한 대기 대신 한도 오류를 처리한다. 주변 대상 제한과 입력 변경 합치기는 후속 최적화이며 이번 버전은 같은 맵 중계를 유지한다.

## wire format / 버전

Game protocol version은 **6**이다. 서버와 Unity 클라이언트를 함께 갱신해야 한다. 기존 version 5 실행 파일은 입장이 거절된다. 기존 MovementInput(opcode 14)은 런타임에서 사용하지 않는다.

| 항목 | 크기 | 내용 |
|---|---:|---|
| MovementActions(opcode 23) header | 30 | mapId u32, generation u64, batchSequence u64, latestClientTick u64, count u16 |
| 행동 레코드 | 63 | sequence/clientTick/jumpId u64, x/y/vx/vy i64, footholdId u32, horizontal i8, grounded u8, kind u8 |
| MovementActionsBroadcast(opcode 24) header | 22 | mapId u32, 수신자 generation u64, 중계 serverTick u64, count u16 |
| 중계 레코드 | 75 | 서버가 정한 characterId u32, latestClientTick u64, 행동 레코드 63바이트 |

좌표·속도는 1/1000 단위 little-endian 정수이다. kind는 Input=0, Jump=1, Land=2, Checkpoint=3, Respawn=4, Fall=5다. 초기 입장/상대 생성 시에는 기존 MovementState로 마지막 저장 상태를 전달한다. 이후의 정기 MovementState 전송은 없다.

행동은 실제 물리 단계 직후의 기준 상태를 갖는다. 수신자는 번호로 중복을 막고 약 200ms의 표시 버퍼에서 행동을 적용한다. 서버 중계 대기 시간은 최신 클라이언트 tick에 반영하며, 수신 후 경과 시간은 클라이언트에서 계산한다. 새 보고가 2초 이상 없으면 추가 예측을 멈춘다.

이는 완전한 전역 시계 동기화가 아니다. 발신자→서버 및 서버→수신자의 실제 지연까지 정확히 복원하지 않으며, 지터·저프레임 상황에서 기준 상태 보정이 필요하다. 다른 PC/실제 원격망에서 시각적 품질을 별도로 확인해야 한다.

## 서버 검증 범위

인증된 연결에서 캐릭터 ID를 결정하고, 맵 generation·배치/행동 순서·공중 잠금·jumpId·방향 범위·위치/속도 범위·보고된 지상 발판을 확인한다. 잘못된 묶음의 크기/범위는 부분 반영 전에 검사한다. 거절한 점프는 방송하지 않는다.

서버는 전체 이동 경로와 충돌을 재현하지 않는다. 보고된 착지가 실제 경로에서 가능했는지, 중간에 벽을 통과했는지는 이 검증으로 보장하지 않는다. 입력 거절에 별도의 즉시 위치 응답을 보내지 않아 5회 송신 상한을 우회하지 않는다.

## 서로 다른 PC에서의 수동 확인

서버 PC에서 version 6 GameServer/LoginServer를 실행하고 `SERVER_BIND_IP`를 서버 LAN IPv4로 설정한다. 클라이언트 PC 두 대에서 최신 Unity 프로젝트/빌드를 실행하고 로그인 Host에 서버 LAN IPv4, Port에 7776을 입력한다. 자세한 네트워크 설정은 [REMOTE_ACCESS.md](REMOTE_ACCESS.md)를 참고한다. fixture를 외부에 공개하지 않는다.

1. A가 Space를 누르면 A는 즉시 점프하고 B도 점프 궤적을 표시한다.
2. A가 공중에서 Space를 여러 번 눌러도 높이가 재설정되지 않는다.
3. A가 착지한 뒤 Space를 새로 누르면 두 화면에서 다시 점프한다. 키를 계속 누른 것만으로 반복 점프하지 않는다.
4. 이동 중 방향 전환·키 해제·채팅 포커스·창 비활성화에서 상대도 수렴하는지 확인한다.
5. 맵 변경·재입장 뒤 이전 행동이 새 캐릭터 상태에 적용되지 않는지 확인한다.
6. 송수신 횟수와 바이트 수, 점프 표시 지연, 위치 오차, LERP/즉시 보정 횟수를 측정한다. LAN 테스트 다음에 원격 서버에서 반복한다.
