# 장비·드롭 확장과 정상 종료의 후속 적용 순서

장비·드롭 확대와 영속 피격 저널은 이번에 런타임에 구현하지 않는다. 현재 무기·모자, 목검 +5 공격력, 모자 -2 피격 피해와 기존 드롭을 유지한다. 아래는 DB·서버·패킷·UI를 함께 바꿀 때의 적용 계약이다.

## 장비 확장 순서

1. 카탈로그와 저장 형식 버전부터 분리한다. 아이템 정의와 개별 장비 인스턴스를 구분하며 기존 1/2 아이템·무기/모자 위치를 그대로 매핑한다.
2. 다음 묶음에서 상의·하의·신발·장갑을 추가한다. 보조무기·여러 반지 칸은 중복 착용/계산 규칙을 정한 뒤 추가한다.
3. 서버 능력치 계산과 착용 트랜잭션을 먼저 검사하고 그 결과를 표시할 새 snapshot·UI를 함께 배포한다.
4. 장비 드롭은 카탈로그·착용·거래가 같은 인스턴스 모델을 사용하는 것을 확인한 뒤 추가한다.

장비 정의 필드는 item_id, category, max_stack, equipment_type, required_level, tradeable, catalog_version과 기본 능력치다. 인스턴스는 instance_id, owner_character_id, item_id, 개별 옵션 버전을 갖는다. 표시 이름·아이콘과 서버 판정에 쓰는 능력치의 버전을 대응시킨다.

장착 위치(position_id)와 종류(slot_type)를 나눈다. 위치 정의의 (position_id,slot_type), 아이템 허용 위치의 (item_id,slot_type)를 각각 고유 키로 두고 장착 행이 이 조합을 참조하도록 한다. 여러 반지 칸도 같은 종류를 허용하는 서로 다른 위치로 표현한다. 캐릭터·위치의 유일성과 장비 인스턴스의 단일 장착 제약을 유지한다.

현재 character_item_instances의 item_id IN (1,2) 제약과 character_equipment의 무기/모자 고정 CHECK를 이관한다. 아이템 ID만 추가한 뒤 기존 CHECK에 걸리게 두지 않는다. 슬롯·착용 행의 instance_id/소유자/item_id 복합 외래 키는 유지한다. 거래로 소유자를 옮길 때는 기존 참조 제거 → 인스턴스 소유자 변경 → 새 슬롯 참조의 순서를 사용한다.

## 능력치와 저장

계산 순서는 기본값 + 장비 고정 합산 → 비율 보정 → 상하한 제한이다. 비율은 basis point 정수(10,000=100%)로 정의하고 중간값은 충분한 폭의 정수를 사용한다. 반올림 규칙을 고정해 서버/표시 계산 차이를 막는다.

현재 공격력 20+목검5와 피격 피해 max(1,10-모자2)는 새 정의로 옮겨도 동일해야 한다. 기존 캐릭터의 전투 수치가 마이그레이션만으로 바뀌는 것은 별도 밸런스 변경으로 취급한다.

착용/해제는 캐릭터 잠금 → 소유 인스턴스·위치·착용 조건·revision 확인 → 슬롯/장착 위치 교체 → 최종 능력치 계산 → 최대 HP/MP와 현재 수치 제한 → revision 갱신을 같은 트랜잭션에서 처리한다. 최대치 증가로 현재 HP를 자동 회복하지 않으며 HP0은 장비 교체로 부활하지 않는다. 최대치 감소 시 현재 수치만 새 최대치 이하로 제한한다.

현재 고정 2부위 snapshot은 부위 개수·위치 ID·인스턴스·공개 외형 ID를 명시하는 구조로 바꾼다. 네트워크 버전을 올리고 구버전은 접속 단계에서 거절한다. 거래 기록의 250바이트 기존 형식은 별도 reader로 유지한다. 다른 플레이어에게는 공개 외형만 전달하고 개인 인벤토리는 보내지 않는다.

## 몬스터 정의와 드롭 설정

몬스터 종류의 화면 식별자와 서버 정의 ID를 분리한다. monster_definition_id가 HP·공격·드롭 표를 참조하고 현재 kind 0..2는 표시용 매핑으로 유지한다. 드롭 설정은 다음과 같은 CSV 필드로 시작한다.

```text
monster_definition_id,entry_id,item_id,min_quantity,max_quantity,probability_ppm,roll_group,catalog_version
1001,1,101,1,2,700000,0,1
1001,2,1,1,1,10000,1,1
1001,3,2,1,1,20000,1,1
```

roll_group=0은 독립 추첨이며 확률 합계를 100%로 제한하지 않는다. 양수 그룹은 배타 추첨이고 합계가 1,000,000 이하이어야 한다. 남은 확률은 미지급이다. 위 값은 형식 예시이며 현재 드롭 확률을 변경한 데이터가 아니다.

시작 시 존재하지 않는 몬스터/아이템, 중복 (monster_definition_id,entry_id), 수량 0·역전·표현 범위 초과, 확률 음수·1,000,000 초과, 배타 그룹 합 초과, 알 수 없는 카탈로그 버전과 사망 한 번의 최대 생성 개수를 거절한다. 초기 생성 상한은 사망당 8개 드롭을 제안하고 필드 드롭 상한과 함께 검증한다.

수량이 최대 중첩보다 크면 필요한 여러 슬롯에 나누는 정책을 명시한다. 무조건 잘라 버리거나 일부만 지급하지 않는다. 장비 수량은 필요한 인스턴스 수이며 초기 설정은 항목당 1개로 제한하고 다량 장비 지급은 별도 검사 후 허용한다.

난수는 서버에서 사망 사건마다 한 번만 추첨한다. death_event_id, drop_id, catalog_version, 추첨 아이템·수량을 연결한다. 지급 재시도·조회는 재추첨하지 않는다. 필드 드롭을 재시작 후에도 유지하려면 사망/추첨 결과 자체를 저장하는 추가 범위가 필요하며 현재 메모리 드롭의 유실 정책과 구분한다.

## 장비 획득 트랜잭션

1. 캐릭터 소유권·인벤토리 행을 잠근다.
2. drop_id의 기존 지급 기록을 확인한다. 이미 지급했으면 현재 인벤토리와 결과만 조회한다.
3. 현재 revision·획득 가능 상태·슬롯 여유를 검사하고 전체 지급 결과를 먼저 계산한다.
4. 필요한 모든 장비 인스턴스를 만들고 비어 있는 슬롯에 연결한다.
5. 지급 기록·생성한 인스턴스 목록·revision을 인벤토리와 함께 커밋한다.
6. 성공 확인 뒤 필드 드롭을 제거한다. 결과가 불명확하면 예약 상태와 같은 번호를 유지하고 조회한다.

기록 구조에는 drop_id의 단일 지급 제약과 (drop_id,instance_id)의 생성 목록을 둔다. 장비 소유자가 거래로 바뀌어도 지급 기록을 새 장비 생성 명령으로 해석하지 않는다. 지급 당시 수령자와 현재 소유자는 다른 정보다. 저장 후 응답을 잃으면 현재 인벤토리를 복구하며 과거 인스턴스를 다시 넣지 않는다.

필수 검사는 동시 획득, 중복 번호, 빈 슬롯 부족, 여러 슬롯 중 일부만 가능한 경우, 첫 인스턴스 생성 후 실패, 슬롯 연결 후 실패, 커밋 뒤 응답 유실, 재접속, 장비 거래 후 과거 획득 조회, 설정 버전 교체 중 지급이다.

## 미확정 피격의 운영 선택

현재는 커밋된 피격만 보존하며 메모리에 남은 피격은 종료 시 유실될 수 있다. 이번 질문의 운영 정책 답변 전에는 이 동작을 바꾸지 않는다.

테스트 단계에서 현재 정책을 유지한다면 재접속으로 미확정 피해를 피할 수 있는 제한을 명시한다. 운영에서 이를 허용하지 않으면 damage_operation_id, 대상, 피해, 발생 generation, 접수 시각, 처리 상태를 영속화하는 저널이 필요하다. 접수 저장과 HP 확정의 경계를 정하고 HP 변경과 저널 완료 표시는 같은 트랜잭션에서 처리한다.

DB 완전 중단 중에도 피격 접수를 보존해야 한다면 DB 저널만으로는 부족하다. 로컬 저널의 동기 기록, 손상 복구, 디스크 부족, 재전송, 서버 인스턴스 식별과 중복 방지까지 별도 범위로 정한다. 저널 없이 메모리 큐를 길게 유지하는 것을 영속 보존이라고 부르지 않는다.

과거 생명 주기의 피해를 부활 뒤에 재생하지 않도록 combat_life_id를 별도로 저장하는 방안을 적용한다. 오래된 이벤트를 단순 만료시키면 피해 회피가 다시 가능하므로, 완료/폐기 사유와 운영 복구 규칙을 함께 정한다.

## 정상 종료 절차

초기 운영 제안은 전체 배출 제한 15초다. 값은 설정으로 두고 DB 연결/조회/잠금 제한 시간과 함께 검토한다. 현재 무한 실행 루프에 이 절차가 구현됐다고 기록하지 않는다.

| 단계 | 처리 |
|---|---|
| 신규 유입 차단 | 게임 accept·입장 티켓·새 캐릭터 입장 차단. LoginServer에 종료 중 상태를 알려 새 입장 라우팅 중지 |
| 새 변경 차단 | 이동·공격·획득·물약·장비 변경·새 거래 확정 거절. 신규 몬스터 전투도 중지 |
| 편집 중 거래 | 초대/편집은 취소 응답. 이미 확정 중인 거래는 취소로 바꾸지 않음 |
| DB 배출 | 진행 중 작업의 완료·조회·동일 번호 재시도를 계속 처리. 아직 시작하지 않은 취소 가능한 조회는 취소 |
| 제한 도달 | 남은 번호·종류·대상·미확정 수를 기록. 성공 응답을 만들지 않음. 운영 정책에 따라 저널 복구 대상으로 유지 |
| 연결 종료 | 남은 최종 결과의 송신 대기와 IOCP 완료를 정리한 뒤 세션/플레이어 제거 |
| 자원 종료 | DB 작업 스레드가 공유 Connection을 더 이상 쓰지 않는 것을 확인한 뒤 Connection·Map·저장소 파괴 |

현재 CharacterRepository 소멸자는 대기 작업을 버리므로 이를 배출 절차로 재사용하지 않는다. StopAcceptingJobs와 DrainUntil 같은 명시적 단계를 두고 취소 가능한 조회와 커밋 불명확 변경을 구분해야 한다. Windows 종료 콜백에서는 DB·네트워크 정리를 직접 수행하지 않고 종료 요청 플래그만 전달한다.

정상 배출·DB 중단·커밋 직후 응답 유실·양측 거래 참가자 종료·배출 제한 초과·강제 종료·재시작을 각각 검사한다. 정상 종료의 15초 배출이 전원 장애나 강제 종료의 영속 보장을 대신하지 않는다.
