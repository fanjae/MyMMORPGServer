## 1. 맵 데이터와 서버 이동 검증

현재 `data/maps.csv`에서 맵별 ID, spawn, 경계, 속도와 누적 허용량을 읽습니다. Free 맵의 `Map::MovePlayer()`는 소속·좌표 범위·속도를 검증합니다. Platformer 맵은 서버 20ms tick에서 입력으로 이동·점프·중력·발판/벽 충돌을 계산하고 Unity가 같은 지형으로 예측합니다. 절대 좌표 요청은 Platformer에서 거절합니다.

이동 구현은 첫 단계의 자유 이동 검증 이후 횡스크롤 이동으로 확장합니다.

| 선택 | 구현 범위 | 현재 클라이언트에 미치는 영향 |
|---|---|---|
| 자유 이동 유지 | 맵 경계, 사각형 장애물, 이동 속도와 서버 위치 보정 | 방향키 이동 유지, 큰 절대 좌표 이동은 거절될 수 있음 |
| 횡스크롤 이동 | 발판 선분, 좌우 이동, 점프, 중력, 착지, 벽 충돌과 서버 위치 보정 | 위아래 자유 이동을 실제 횡스크롤 입력으로 교체 |

자유 이동을 선택한 경우에도 테스트 장애물은 실제 발판 데이터와 구분합니다. 메이플 형태의 이동을 구현할 때는 발판 ID, 양 끝 좌표, 인접 발판 관계, 일방향 착지, 사다리 등의 규칙을 별도로 정의해야 합니다.

공통 구현 사항은 다음과 같습니다.

1. 맵별 ID, spawn, 경계와 충돌 정보를 데이터로 정의하고 서버와 Unity가 같은 좌표 단위로 사용합니다. 기존 변환은 서버 20단위가 Unity 1단위입니다.
2. 데이터 로딩 시 중복 ID, 잘못된 경계, 맵 밖 spawn, 충돌 영역 안 spawn을 검사합니다.
3. 서버의 단조 증가 시간과 마지막 이동 상태를 이용해 이동 거리를 검사합니다. 클라이언트가 보낸 시간만으로 이동을 허용하지 않습니다.
4. 네트워크 지연 허용량은 제한된 이동 여유로 관리합니다. 패킷마다 고정 허용 거리를 더하면 고빈도 요청으로 제한을 우회할 수 있으므로 누적 허용량에도 상한을 둡니다.
5. 장애물을 통과하는 이동은 이전 좌표에서 새 좌표까지의 경로를 검사합니다. 목적지만 검사하면 장애물을 건너뛰는 요청을 막지 못합니다.
6. 정상 이동과 거절된 이동 모두 요청자에게 서버 확정 좌표를 전달합니다. 상대에게는 허용된 이동만 브로드캐스트합니다.
7. 정상적인 이동 거절은 위치 유지와 결과 응답으로 처리합니다. 현재 패킷 핸들러의 `false` 반환은 연결 종료로 이어질 수 있으므로 거절 결과와 네트워크 실패를 구분합니다.
8. 맵 이동과 입장 시 이동 시간 및 허용량을 초기화하고, 서버가 정한 spawn 이동은 일반 이동 속도 검증과 분리합니다.

현재 Unity 이동 속도는 초당 서버 80단위, 전송 간격은 50ms입니다. 첫 검증 단계는 이 값을 기준으로 구성하되 설정 값으로 관리할 수 있게 합니다. 횡스크롤 선택 시 수평 속도와 점프·낙하 규칙은 추가 결정이 필요합니다.

현재 `MoveRequest`에는 Map ID와 요청 번호가 포함되며 `MoveResponse`를 통해 확정 좌표를 전달합니다. 클라이언트는 요청 번호와 맵을 확인해 이전 응답이 새 입력을 덮지 않도록 처리합니다. 서버, C++ TestClient, Unity Protocol 및 자동 통합 테스트를 함께 수정했고, 이전 Windows 빌드는 새 프로토콜과 호환되지 않습니다.

현재 절대 좌표 `Send`는 일반 이동 요청입니다. 서버 속도 제한을 우회하는 순간이동 기능으로 자동 전환하지 않습니다. 개발용 순간이동이 필요하면 별도 권한과 실행 설정을 정한 뒤 추가합니다.

검증 기준:

- 경계 안 정상 이동은 허용되고 요청자 및 같은 맵 상대 좌표가 일치
- 경계 밖, 과도한 속도, 장애물 통과 요청은 거절되고 상대 좌표 유지
- 거절 후 로컬 목표가 서버 위치로 보정되고 정상 이동 재개
- 다수의 짧은 요청과 장시간 정지 후 큰 이동도 속도 제한을 우회하지 못함
- 정수 최대·최소 좌표 요청에서 거리 계산 overflow 없이 거절
- 맵 전환과 재입장 후 정상 이동 허용, 이전 맵 응답에 의해 위치가 바뀌지 않음
- 기존 Map-local 입장·이동·채팅·맵 변경·연결 종료 테스트 유지

## 2. 채팅 빈도와 재접속 보강

채팅은 현재 Map의 Player에게만 전달되며 발신자에게도 수신 패킷을 보냅니다. 빈도 제한은 없습니다. 서버는 연결 종료 시 Map과 PlayerManager에서 Player를 제거합니다.

다음 구현에서는 인증된 사용자 단위로 채팅 빈도를 제한하고, 맵 변경으로 제한이 초기화되지 않게 합니다. 허용량을 넘긴 채팅은 브로드캐스트하지 않으며 송신자에게 제한 결과를 표시합니다. 공백, 문자열 종료, UTF-8 유효성 등은 서버에서도 검증합니다.

재접속은 연결 종료 후 월드 객체와 입력·송신 상태를 정리하고 새 LoginServer 인증부터 진행합니다. 이미 소비한 authKey를 재사용하지 않습니다. 이전 연결의 수신 이벤트와 송신 완료가 새 연결 상태를 변경하지 않도록 세션을 구분합니다. 자동 재로그인과 비밀번호 저장 여부는 별도 사용자 정책이 필요하므로 우선 사용자가 다시 로그인하는 흐름을 검증합니다.

검증 기준은 제한 안 정상 채팅, 제한 초과 시 상대에게 미전달, 시간 경과 후 정상 전송, 맵 변경 후 제한 유지, 연결 종료 후 다른 창의 Player 제거, 같은 캐릭터 재입장과 이전 세션 이벤트 무시입니다.

## 3. Channel과 Map의 관리 경계

Channel 도입 시 Map ID만으로 런타임 맵을 식별하지 않고 Channel ID와 Map ID를 함께 사용합니다. 같은 Map ID라도 Channel이 다르면 Player와 Monster 상태 및 일반 채팅이 분리되어야 합니다.

Channel은 해당 Channel의 MapManager와 맵 갱신 실행을 관리하고, Map은 소속 객체와 Map-local 전파를 관리합니다. 계정·캐릭터 중복 접속 검사는 현재 PlayerManager와의 관계를 정리하여 Channel을 바꿔도 유지합니다. 멀티 스레드 실행을 도입할 때는 같은 Map의 상태 변경 순서를 먼저 보장해야 합니다.

첫 단계에서는 소유 관계와 전환 흐름을 설계합니다. Channel 선택과 이동을 실제로 구현할 때 로그인 티켓, 입장 응답, 이동 결과에 필요한 식별자를 함께 확장합니다.

## 4. 실제 게임 UI

현재 IMGUI 컨트롤러는 프로토콜 테스트용입니다. 실제 화면은 별도 UI Toolkit 화면과 입력 계층으로 구성하며 `NetworkManager`와 `Protocol`을 연결합니다. 로그인, 캐릭터 선택, 게임 HUD·채팅 순서로 전환합니다.

실제 UI를 추가하기 전에 `TestClientController.CreateTestClient()`의 자동 생성을 테스트 실행에 한정합니다. WorldManager에 있는 테스트 사각형 생성과 카메라 처리는 실제 캐릭터·맵 표현 계층으로 옮길 범위를 정합니다.

Unity의 [런타임 UI 공식 예제](https://docs.unity3d.com/kr/current/Manual/UIE-runtime-examples.html)는 런타임 화면과 캐릭터 선택 목록 구성을 설명합니다. 프로젝트 버전에 맞는 API를 확인하며 UXML/USS와 화면 컨트롤러를 작성합니다.
