## 수정과 재현

### 완료 결과와 인벤토리가 함께 유실된 거래

실제 서버에서 최종 확정 요청은 전달하고 커밋 뒤의 Completed와 requestId=0 인벤토리 응답만 프록시에서 버렸다. 기존 코드에서는 QUERY가 Completed만 돌려주어 클라이언트의 아이템·메소가 이전 상태에 남았다. 수정 전 검사가 `Trade QUERY completed without restoring lost inventory state`로 실패했다.

완료 거래의 메모리 상태만 반환하지 않고 DB의 현재 인벤토리와 완료 기록을 함께 다시 전달하도록 수정했다. 같은 조회 반복은 교환을 다시 수행하지 않는다. 수정 후 물약 수량·메소·revision 복구 검사가 통과했다. 근거: artifacts/trade-loss-before-2026-10-16.log, trade-loss-after-2026-10-16.log, trade-loss-final-2026-10-16.log.

### 늦은 응답과 빈 거래

- 진행 중 거래가 있을 때 과거 번호 QUERY는 현재 진행 상태를 우선 반환한다.
- 클라이언트는 다른 거래의 늦은 종료 응답으로 현재 거래를 닫지 않고, 이미 끝난 같은 거래를 늦은 Editing 응답으로 다시 열지 않는다.
- 양측 제안이 빈 상태의 최종 확정 거절 시 두 번째 확인을 원복해 서버에 양측 확인만 남지 않도록 수정했다.
- 연결 해제 시 이전 UI 제안·금액·선택 목록을 비워 복구 QUERY에 이전 제안을 붙이지 않는다.
- 슬롯 부족·오래된 제안·만료·결과 대기를 실제 안내 문장으로 표시한다. 파괴된 UI에 늦은 송신 실패가 도착하면 표시 접근을 중단한다.

### 거래 조회와 미확정 피격 복구의 중첩

별도 캐릭터 1002의 HP 변경만 거절하는 임시 DB 제약을 걸고 채널2에서 피격 복구를 발생시켰다. 이때 존재하지 않는 과거 거래 번호를 QUERY하면, 조회의 인벤토리 반영이 PauseCombat(false)를 호출해 아직 확정하지 못한 피격의 조작 제한을 풀었다. 수정 전 `Trade receipt lookup lifted active damage recovery`로 실제 서버 재현에 실패했다. 근거: artifacts/trade-recovery-before-channel-2026-10-16/client.err. 처음 채널을 분리하지 않은 준비 시도에서는 부하 캐릭터가 피격 대상으로 선택되어 대기 시간이 초과했으며 이를 해당 오류의 재현 증거로 사용하지 않는다.

ApplyTradeInventory가 _recovering 상태를 보존하도록 수정했다. 수정 후 독립 TradeRecovery 프로필에서 조작 제한 유지·공격 거절·같은 피해의 한 번 확정·정상 재개가 통과했다. 근거: artifacts/extra-recovery-2026-10-16.log, headless-2026-10-16/TradeRecovery-d2dc85154065482cb194e33b8b57f1cc/client.out. 임시 제약은 재현 실패/종료 경로에서도 제거했다. 부하 계정 3001번 이후의 데이터는 변경하지 않았다.

순수 C# 이동·입력·패킷·거래 상태 검사 23개 묶음이 통과했다. 분리한 MySQL에서도 기존 인벤토리·장비·복구와 거래의 23개 묶음이 통과했다. 근거: artifacts/client-regression-2026-10-16.log, database-2026-10-16.log. 두 23개는 서로 다른 검사 묶음이다.

기존 이동 TCP와 필드 TCP 검사도 0±0/80±35/150±60ms 세 조건에서 통과했다. 근거: artifacts/movement-tcp-2026-10-16.log, field-tcp-2026-10-16.log. 이 fixture 검사는 실제 DB를 연결한 서버 검사와 구분한다.

기존 C++ NetworkReliability 회귀도 통과했다. 현재 변경하지 않은 Map·전투·중계 코드의 검사 실행 파일을 사용했으며 거래 변경 자체는 실제 DB/서버 검사로 확인했다. 의도한 잘못된 bind·송신 대기열 상한 오류 출력은 해당 실패 격리 검사의 일부다. 근거: artifacts/server-regression-2026-10-16.log. 느린 수신자 계측 추가 뒤 순수 C# 23개 묶음도 재통과했다. 근거: artifacts/client-regression-final-2026-10-16.log.

## 실제 이동/주변 목록의 자동 재현

96명 부하 집단과 별도로 진단 계정을 사용했다. 부하 집단은 채널1, 이동은 채널2, 경계는 채널3이다. 거래/피격 복구 재현도 채널2에서 수행했고, 채널 분리 전 준비 시도는 채널1에 잠시 접속했다. 서버 전체 계측과 같은 채널의 일부 전송량에는 이 부가 진단 연결도 포함된다. 부하 클라이언트가 집계하는 96명 집단은 고정이다.

지연 프록시는 20ms 고정 → 150±60ms → 20ms 고정 → 다운로드 4초 정지 → 재수신으로 전환했다. 실제 서버의 이동 행동을 RemoteMotion3D에 넣고 20ms 간격으로 표시 상태를 CSV에 기록했다. 최종 반복 검사에서는 60개 행동, Jump/Land 각 4개뿐 아니라 샘플링한 표시 상태의 점프/착지도 각 4개·방향 변화 13개·복구 snap 2개를 확인했다. 악화 구간 버퍼 최고 400ms, 안정화 끝 282.42ms였고 4초 수신 중단 이후에는 다시 400ms였다. 중단 뒤에도 곧바로 200ms가 된다고 주장하지 않는다. 예측 정지·재수신·맵 이탈/재입장 기준 상태 검사도 통과했다.

근거: artifacts/movement-transitions-2026-10-16.log 및 movement-transitions-2026-10-16/movement-transitions.csv. CSV는 수치 표시 모델의 결과이며 실제 Unity 화면 프레임의 자연스러움 측정은 아니다.

서버 보정 항목은 현재 3D 방식의 범위를 함께 명시한다. 3D 서버는 클라이언트 행동의 범위·순서·상태 전이를 검증해 중계하며 물리를 매 tick 다시 계산하지 않는다. Client3DController는 자기 MovementState3D를 입력 확인/재실행용 보정으로 적용하지 않는다. 이번 초기화 검사는 상대의 새 snapshot·수신 재개 기준점·맵 generation 전환에 대한 것이며, 과거 2D에서 구현했던 서버 확정 입력 재실행을 현재 3D에서도 검증했다는 뜻은 아니다. 3D 본인 위치의 서버 권위 보정은 별도 구현 범위다.

몬스터·드롭 주변 목록은 실제 서버에서 세 번 왕복했다. 먼 위치에서 제거되고 가까운 위치에서 같은 드롭 ID가 복귀하는 것, 멈춘 캐릭터의 몬스터 목록이 16m 안인 것을 확인했다. 두 캐릭터는 16m 밖에서도 플레이어 목록에 남아 현재 플레이어 전체 맵 전송 동작을 확인했다. Unity 표시 객체의 Instantiate/Destroy나 풀 재사용을 측정한 결과는 아니다. 근거: artifacts/field-visibility-2026-10-16.log.

기본 jumpSpeed=160, gravity=400을 사용하는 모터와 실제 서버 패킷으로 높이 30.240단위(1.512m)의 Miss, 29.920단위(1.496m)의 Hit·20피해를 양측에서 확인했다. 실제 키 입력은 사용하지 않았다. 경계 안이어도 전방·거리·차폐·살아 있는 대상 조건은 별도로 필요하다. 근거: artifacts/jump-boundary-2026-10-16.log. 독립 재실행 모드는 움직이지 않는 대상 fixture를 사용해 이 조건을 고정한다.

### 최종 바이너리의 밀집·분산·느린 수신자 비교

수신량은 정상 수신자 집단의 표본이며 느린 연결은 제외한다. 서버 시간은 준비를 포함한 프로세스 전체의 완성된 보고 구간이다. 밀집/분산 실제 시간은 각각 120.016/120.004초, 느린 조건은 120.005초다. 짧은 표본의 차이를 장시간 평균이나 격자 구현의 효과로 일반화하지 않는다.

분산 전 준비 이동 후 실제 좌표는 (-3.9,-286.1), (-3.9,26.1), (-316.1,-286.1), (-316.1,26.1) 네 곳이었다. 이후에는 멈춘 상태로 공격한다. 최종 몬스터 목록은 밀집 92마리, 분산 집단별 48/64/75/102마리였다. 몬스터 수신량이 약 21.37% 감소했고 전체 수신량은 약 8.55% 감소했다. 플레이어 중계는 여전히 같은 맵 전체이며 최대 대기는 비슷하게 남았다.

느린 연결은 인증/준비 후 다운로드를 1,024바이트/초로 제한했다. 제한이 적용된 전송 185프레임·28,317바이트를 기록한 뒤 해당 연결의 TCP 송신 대기가 1MiB 한도에 걸려 종료됐다. 직전 대기 출력은 1,044,725바이트이며 추가 프레임을 넣는 시점에 한도를 넘긴다. 정상 95명은 120초 끝까지 연결·생존·전투 복구 해제·송신 대기 0을 유지했다. 이 조건의 movement sendFailures=1, field failures=1은 해당 느린 연결 종료와 함께 발생했으며 실패 카운터 0인 조건으로 기록하지 않는다. 이동 중계 FIFO 초과는 세 단기 표본 모두 0이었다.
