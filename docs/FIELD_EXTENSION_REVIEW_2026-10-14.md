# 장비·드롭 확장과 대기 피격 정책 검토 — 2026-10-14

이번 작업은 기존 기능 검증·오류 수정까지 진행한다. 아래 구조 변경은 검토안이며 구현하지 않았다. 채널 수·정원·서버 간 이전 등의 추가 구현도 대기한다.

## 장비 부위와 능력치

현재 `Protocol/FieldPacket.h`와 Unity `InventoryData`는 무기·모자 2칸을 고정 배열로 저장한다. `InventoryService::EquipmentSlot`, 장비 UI와 DB의 인스턴스 제약은 아이템 1·2만 지원한다. `Player::AttackDamage`는 무기를 착용하면 25, `IncomingDamage`는 모자를 착용하면 8로 계산하므로 새로운 장비를 넣기만 해서는 올바른 능력치가 적용되지 않는다.

다음 단계에서는 부위 번호와 아이템 정의를 먼저 통일한다. 우선 무기·모자·상의·하의·신발·장갑·방패/보조무기 정도의 부위를 고정된 식별자로 정의하고, 지원 여부·착용 조건·중복 부위·양손 무기 제한을 서버에서 검증한다. 반지 여러 칸 등은 부위와 착용 위치를 별도로 표현한다.

아이템 정의에는 분류·최대 중첩·허용 부위·기본 공격력/방어력/최대 HP·MP를 두고, 소유 인스턴스에는 인스턴스 ID·아이템 ID·소유 캐릭터·개별 옵션·강화 상태를 둔다. 아이템 정의를 바꿔도 소유권과 고유 번호는 유지한다. 카탈로그는 버전과 유효성 검사 후 서버가 읽고 클라이언트에는 표시용 정보만 제공한다.

능력치는 기본 능력치 → 장비 합산 → 비율 보정 → 최솟값/최댓값 제한 순서로 서버에서 계산한다. 착용 트랜잭션에서 장비 이동과 최종 HP·MP 한도 조정을 함께 확정하고 revision을 한 번 올린다. 최대 HP가 늘었다고 현재 HP도 자동 회복시키지 않는다. 최대치가 줄면 현재치를 새 최대치 이하로 제한한다. 사망 상태에서는 최대치 변경으로 부활하지 않는다.

확장 시 필요한 변경은 다음과 같다.

- DB의 `ck_instance_item` 제한과 착용 부위 제약을 카탈로그 검증에 맞게 변경한다.
- 소유 인스턴스가 인벤토리와 착용 위치에 동시에 존재하지 않도록 현재 중복 검사·외래 키·행 잠금을 유지한다.
- 장비 칸 수가 달라지면 snapshot 크기와 protocol version을 함께 변경한다. 현재 protocol 11의 1,742바이트 인벤토리는 그대로 확장하지 않는다.
- 슬롯 부족·교체·동일 인스턴스 중복·사망 중 착용·최대 HP 감소·장비 변경과 피격의 동시 요청을 DB 트랜잭션과 UI에서 검증한다.

## 몬스터별 드롭 설정

현재 `Map::CreateDrop`은 모든 몬스터에 빨간 물약 한 개를 생성하고, `InventoryService::Mutate`는 소비·기타의 일부 아이템만 지급한다. 장비 획득은 아직 지원하지 않는다.

드롭 설정은 `monster_definition_id, entry_id, item_id, min_quantity, max_quantity, probability_ppm, roll_group` 형태의 파일이나 DB 테이블로 관리하는 방식을 제안한다. 독립 추첨과 배타적 추첨 그룹을 명확히 구분하고, 확률 단위는 정수 0..1,000,000으로 고정한다. 배타적 그룹의 확률 합은 상한을 넘을 수 없다. 잘못된 아이템 ID·0 수량·역전된 범위·중복 entry·과도한 최대 드롭 수는 시작 전에 거절한다.

몬스터 사망 시 서버가 한 번 추첨해 확정된 아이템·수량을 드롭에 기록한다. 클라이언트가 확률이나 결과를 제출하지 않는다. 재조회·지급 재시도 때 다시 추첨하지 않는다. 몬스터 HP와 드롭은 현재 메모리 상태이므로 서버 재시작 후 유지가 필요해지면 몬스터 사망 번호·추첨 결과·유효 시간의 영속화도 별도 범위로 포함한다.

## 장비 획득 트랜잭션

현재 드롭 ID의 UNIQUE 지급 기록과 인벤토리 변경은 한 트랜잭션이다. 장비에도 이 경계를 유지해야 한다.

1. 인증된 소유 캐릭터 행을 잠그고 드롭 ID의 기존 지급 결과를 확인한다.
2. 카탈로그·수량·장비 탭 빈 칸을 검증한다. 공간이 없으면 인스턴스나 지급 기록을 남기지 않는다.
3. 확정된 드롭 정보로 장비 인스턴스를 만들고 해당 슬롯에 연결한다. 장비 수량이 여러 개면 각 개체의 인스턴스와 필요한 슬롯을 모두 준비한다.
4. 지급 기록에 생성 인스턴스 ID들을 연결하고 인벤토리 revision과 함께 커밋한다.
5. 커밋이 확인된 뒤 필드 드롭을 제거하고 결과를 보낸다. 응답 유실은 동일 드롭 결과 조회로 복구한다.

중복 지급·고아 인스턴스·일부 수량 지급을 막는 것이 핵심이다. 같은 드롭 ID를 재시도하면 이미 생성된 인스턴스 ID를 반환해야 하며 새 인스턴스를 만들면 안 된다. 현재 임의 인스턴스 번호는 최초 인벤토리 생성에서만 발급하므로 장비 지급은 별도 구현이 필요하다.

## 서버 종료와 미확정 피격

현재 정책은 다음과 같다.

| 종료 시 상태 | 현재 결과 |
|---|---|
| 피격 처리 번호와 HP가 함께 커밋됨 | DB에 보존하며 같은 번호의 재시도는 중복 적용하지 않음 |
| DB 트랜잭션이 커밋 전 실패·취소됨 | HP와 처리 기록을 함께 롤백 |
| DB 결과가 불명확하고 서버가 계속 실행됨 | 같은 처리 번호로 재시도하며 신규 전투를 중단 |
| 세션 또는 서버 프로세스가 종료됨 | 메모리 대기 피격은 폐기하며 새 로그인은 저장된 상태로 시작 |
| 커밋과 프로세스 종료가 경합함 | DB에 실제로 커밋된 상태가 기준이며 메모리만으로 적용 여부를 추정하지 않음 |

`GameSession::OnDisconnected`는 활성 작업을 취소하고 대기열을 지운다. `CharacterRepository` 종료도 대기 작업을 버린다. 현재 GameServer의 일반 실행 루프에는 별도 정상 종료 절차가 없으므로 강제 종료에서 대기 피해의 처리를 보장할 수 없다. 이미 커밋한 피격을 되돌리지는 않는다.

현재 테스트 단계에서는 **커밋된 피해만 보존하고 미확정 메모리 피해는 폐기하는 정책을 유지**하는 방안을 권장한다. DB 장애로 전투가 멈춘 캐릭터에게 재접속 뒤 오래된 피해가 몰아서 적용되는 일을 피할 수 있고, 현재 상태 모델과 일치한다. 이 정책은 재접속으로 미확정 피해를 회피할 수 있다는 제한을 가진다.

피해 회피를 막아야 하는 단계에서는 요청을 받았다는 사실 자체를 영속화해야 한다. 처리 번호·캐릭터·피해량·필드/생성 번호·발생 시각·상태를 저장하는 대기 피격 저널을 두고, 같은 번호로 HP 변경과 처리 완료를 한 트랜잭션에서 확정한다. 재시작 시 오래된 필드 사건을 재생할지 폐기할지, 사망·부활 이후의 피해를 어떻게 취급할지도 함께 정의해야 한다. DB가 완전히 중단된 동안에도 보존하려면 로컬 영속 저널과 손상·재전송·디스크 부족 정책이 필요하므로 별도 설계 범위다.

정상 종료의 대기 작업 배출은 보완할 수 있지만 프로세스 강제 종료의 영속 보장을 대신하지 않는다. 어느 방안도 이번 검증 작업에서 구현하지 않았다.
