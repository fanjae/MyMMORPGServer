# 기본 공격·인벤토리·장애 복구·전송 검증 — 2026-10-14

사용자 승인에 따라 기존 Compose의 `mymmorpg-mysql`과 `mymmorpgserver_mysql_data`를 초기화하고 최신 001~004 SQL을 적용했다. 별도 `release_mysql_data` 볼륨은 사용하거나 삭제하지 않았다. 기존 `.env`의 `DB_NAME`과 `SERVER_BIND_IP`가 붙어 있던 줄바꿈 오류도 수정했다. 서버·3D 실행 파일은 protocol 11로 다시 빌드했다.

## 검사 구분

| 구분 | 수행 방식 | 결과 해석 |
|---|---|---|
| 실제 UI | 동일 PC의 Windows 실행 파일 두 개에 에이전트가 키·클릭·드래그 입력 | Unity 입력·화면·서버 결과·기존 DB를 대조함. 사람이 직접 조작한 검사로 표기하지 않음 |
| 서버·클라이언트 자동 검사 | C++/C# 규칙 검사, 실제 TCP의 0 / 80±35 / 150±60ms 조건 | 입력 규칙·패킷·주변 목록·중복 방지 회귀 검사 |
| 실제 DB 장애 검사 | 기존 MySQL 일시 정지, 실제 커밋 이후 검사 콜백의 결과 유실 | DB 시간 초과와 커밋 이후 불명확한 결과를 구분함 |
| 응답 유실 UI | 실제 서버 앞의 TCP 프록시가 성공 응답과 결과 조회 응답을 폐기 | 지급·소비를 직접 변경하거나 요청을 복제하지 않음 |
| 부하 | 실제 서버의 테스트 계정 2·8·32개 및 Unity 실행 파일의 별도 표시 검사 | 자동 공격/표시 재생이며 실제 사용자 조작 결과와 분리함 |

초기 `baseline-*`, `combat-*`, `verified-*` 창 검사에는 다른 사용자 입력 감지가 있어 관측용 기록으로 보관했다. 사용자가 입력을 멈춘 이후의 `drag-fixed-*`, `range-*`, `wall-*`, `fault-ui-*`, `fault-restored-*`, `final-controls-*`를 확정 결과의 근거로 사용했다. `mode=manual`은 자동 이동 옵션을 사용하지 않은 실행을 뜻하며 입력 주체는 에이전트다.

## 수정한 오류

1. 빠른 드래그가 한 프레임에 끝나면 슬롯 이동 대신 도착 슬롯의 클릭으로 처리되는 현상을 실제 UI에서 두 번 재현했다. 원래 마우스 누름·해제 위치를 입력 이벤트에서 보존해 같은 프레임의 드래그를 복원했다. 다른 탭·바뀐 원본 아이템·잠긴 상태·다른 창·포커스 해제는 거절하고 UI 클릭과 중복 적용하지 않는다.
2. 이동 송신 대기에서 이미 꺼낸 공격이 나중에 취소돼도 전송될 수 있는 경로를 수정했다. 송신 직전 취소 번호와 현재 조작 가능 상태를 함께 검사한다. 같은 이동 확인 구조를 쓰는 획득 대기도 적용했다. 취소된 이전 요청과 새 입력을 구분하는 회귀 검사를 추가했다.
3. 획득 결과 조회 3회가 모두 응답을 잃으면 “조회 중”만 남던 안내를 수정했다. 마지막 5초 응답 제한 뒤 LOOT·Z 안내를 표시하고 재시작·수동 조회에서 다시 확인했다.
4. 클라이언트 획득 거리의 정확한 2m 경계를 서버의 포함 조건과 맞췄다. 장비 슬롯 부족 오류의 서버 응답도 빈 슬롯 안내로 표시한다.
5. 입력 기록의 물약 수량을 고정 슬롯 대신 소비 탭 전체의 아이템별 합으로 계산했다. 슬롯 교환 후 파란 물약을 빨간 물약 수량으로 기록하던 진단 오류를 수정했다. 장비 고유 번호·상대 공격 결과·몬스터 위치·복구 상태도 기록한다.

주석은 기존 코드의 짧은 한국어 설명과 “확인한다 / 유지한다 / 처리하지 않는다” 등의 문장 형식을 따랐다. 장비·드롭의 다음 기능과 채널 추가 기능은 구현하지 않았다.

고정 몬스터·벽은 사거리 판정을 재현하기 위한 명시적 검사 설정이다. 원본 지형은 수정하지 않았으며 일반 서버의 추적·피격 동작과 구분한다. 공중 높이 1.5m를 넘는 정확한 순간의 실제 키 공격과 키를 길게 누른 뒤 차단 상태를 통과하는 동작은 이번 도구의 단일 키 입력 검사로 완료했다고 표기하지 않는다. 높이·유지 입력 차단과 송신 대기 중 취소의 세부 경계는 자동 검사 근거를 함께 사용한다.

## 실제 인벤토리 UI 결과

수정 후 빠른 드래그로 빨간 물약 11+5→16 병합, 파란 물약 8개의 빈 슬롯 이동, 빨간/파란 물약의 슬롯 교환을 확인했다. USE로 빨간 물약 16→15, 파란 물약은 응답 유실 검사에서 8→7·MP 25→45로 한 번 소비됐다.

목검 인스턴스 3의 착용·해제·재착용을 확인했다. 장비 탭을 24칸으로 만든 검사에서는 UNEQUIP이 “No free equipment inventory slot.”로 거절됐으며 원래 장비는 유지됐다. 부족 조건의 임시 장비는 검사 후 제거했다.

서버와 실행 파일을 재시작한 뒤 슬롯 0의 파란 물약 7, 슬롯 8의 빨간 물약 17, 착용 목검 인스턴스 3을 확인했다. 최종 UI 상태와 DB는 `ui-final-database.tsv`로 대조했다. 생명력 증가는 검사 시간을 확보하기 위한 테스트 설정이며 최종 환경 정리에서 원래 최대 HP로 되돌린다.

## 장애 복구 결과

- 기존 MySQL 컨테이너의 응답을 일시 정지했을 때 전투 중단 표시·입력 차단을 확인했다. 중단 중 J는 전송되지 않았고 응답 재개 뒤 재접속 없이 저장 상태를 복구했다. 새 J는 25 피해로 적중했다.
- 실제 DB 연결 두 개를 KILL CONNECTION으로 종료했을 때 `final-controls-2001`의 기록에서 combatPaused=true 뒤 false 복구를 확인했다. 이후 발견한 아래 Unity 창 전환 종료는 별도 실패로 기록한다.
- 같은 기존 MySQL 컨테이너의 별도 검사 스키마에서 실제 커밋 후 콜백이 예외를 내도록 했다. 피격의 동일 처리 번호 재시도, 물약의 이전 revision 재요청, 드롭의 같은 ID 재요청 모두 HP·수량·revision을 두 번 변경하지 않았다. 이 검사는 실제 네트워크의 COMMIT 응답 패킷을 잘라낸 검사와 구분한다.
- 실제 서버의 물약 성공 snapshot을 폐기했을 때 DB는 MP 45·수량 7, 화면은 MP 25·수량 8을 유지했다. 5초 제한 뒤 조회로 MP 45·수량 7을 복구했고 물약 요청을 재전송하지 않았다.
- 획득 성공과 3회의 조회 응답을 폐기해 지급 완료·클라이언트 미확정 상태를 만들었다. 조회 한도 뒤 수동 안내가 나타났다.
- 미확정 상태에서 EXIT GAME으로 종료하고 재실행해 이전 dropId의 결과 조회가 자동 시작되는 것을 프록시 로그로 확인했다. 응답을 허용한 뒤 Z로 Success를 복구했으며 해당 지급 기록은 한 건, 빨간 물약은 16으로 유지됐다.
- 다음 드롭도 LOOT 성공 응답을 잃게 한 뒤 LOOT 수동 조회로 복구했다. 빨간 물약은 17로 한 개만 증가했다.

서버 종료의 메모리 대기 피격과 장비·드롭 확장 범위는 [별도 검토 문서](FIELD_EXTENSION_REVIEW_2026-10-14.md)에 정리했다. 현재 대기 피격은 서버·세션 종료에서 폐기될 수 있으며 영속 저널은 추가하지 않았다.

## 주변 전송과 측정

실제 TCP 수신량은 게임 헤더를 포함한 모든 검사 연결의 합이며 TCP/IP 헤더와 DB 트래픽은 포함하지 않는다. `peakSampledQueuedBytes`는 서버 루프의 송신 전후 표본 최댓값이다. 커널 송신 버퍼의 최대량이나 순간적인 모든 피크를 뜻하지 않는다. `maxAttackUs`는 대상 판정까지의 시간이며 방송·DB 처리 시간은 포함하지 않는다.

생성 요청 3·32·128과 공격자 2·8·32의 9조건 및 128/32명 위치 분산 조건이 통과했다. 요청 128 중 지형과 겹친 6개체는 제외돼 실제 생성 수는 **122**다. 3·32 요청은 각각 3·32개체다. `population-128.txt`로 실제 수를 확인했다. 따라서 서버 측 “128” 결과는 128 생성 요청/122 실제 개체를 뜻한다. 오프라인 표시 검사는 정확히 128개의 표시 개체를 사용한다.

동시 표시 검사와 분리한 32명 핵심 조건의 재측정은 다음과 같다. 각 조건은 준비 후 약 12초 동안 640회 공격 입력을 보냈다.

| 생성 요청 / 실제 개체 | 배치 | 전체 수신 B/s | 몬스터 목록 바이트 / 구간 | 공격 결과 바이트 / 구간 | tick 관측 최대 | 송신 대기 표본 최대 |
|---|---|---:|---:|---:|---:|---:|
| 3 / 3 | 같은 위치 | 266,876 | 204,000 | 1,003,520 | 0.626ms | 135,200B |
| 32 / 32 | 같은 위치 | 410,869 | 1,867,776 | 1,003,520 | 0.601ms | 142,011B |
| 128 / 122 | 같은 위치 | 765,059 | 5,696,544 | 1,003,520 | 0.921ms | 201,873B |
| 128 / 122 | 네 위치 | 652,363 | 4,354,368 | 1,003,520 | 0.665ms | 174,376B |

이동 거절·송신 실패·대기열 초과·tick 따라잡기 제한은 0이었다. tick 스케줄 지연 관측 최대는 16~17ms, 공격 대상 판정 최대는 5~12µs였다. 송신 대기는 공격 묶음 시 증가한 표본이며 연결별 1MB 제한과 단위가 다르다. 실제 느린 수신자·다른 PC·장시간 부하는 검사하지 않았다.

추가 실제 서버 검사에서 네 위치 `(-3.9,26.1) / (-316.1,26.1) / (-3.9,-286.1) / (-316.1,-286.1)`의 주변 몬스터 수는 101/61/74/45, 드롭 수는 25/6/12/1이었다. 이동 거절 없이 서로 다른 목록을 받았다. 자동 경계 검사에서는 16m에 포함, 그 다음 1/1000 서버 좌표에서 제외되는 동작을 몬스터·드롭 각각 세 번 반복했고 같은 바깥 목록의 반복 전송이 없었다.

실제 Unity 온라인 표시에서 12초 동안 조각 232개를 수신했다. 해석·결합 총 5.184ms(조각당 약 0.022ms), 완성 목록의 표시 적용 총 6.247ms였다. 측정 구간에 표시 개체 18개가 생성되고 20개가 제거됐으며 종료 시 114개체였다. 반경 경계의 순찰 진입·이탈은 새 표시 개체를 만들므로 객체 재사용은 후속 최적화 후보다. 표시 적용 시간에는 이후 매 프레임의 보간·렌더링 비용은 포함하지 않는다.

### Unity 표시 비용

3초 준비 뒤 12초, 같은 1100×720 창에서 이름·피해 숫자·공격 표시 조건을 분리했다. 서버 공격 부하·빌드 작업은 함께 실행하지 않았다.

| 개체 수 | 표시 조건 | FPS | p50 프레임 | p95 프레임 |
|---|---|---:|---:|---:|
| 3 | 모두 | 1165.87 | 0.688ms | 2.396ms |
| 32 | 모두 | 998.82 | 0.813ms | 2.846ms |
| 128 | 모두 | 777.88 | 1.167ms | 2.035ms |
| 128 | 이름·피해·공격 표시 없음 | 853.72 | 1.042ms | 1.947ms |
| 128 | 이름만 | 795.20 | 1.138ms | 1.867ms |
| 128 | 피해 숫자만 | 774.90 | 1.167ms | 1.998ms |
| 128 | 공격 표시만 | 813.38 | 1.091ms | 2.119ms |

128 개체에서 표시 모두와 표시 없음의 p50 차이는 약 0.125ms였다. 개별 차이를 더해 전체 비용이라고 계산하지 않는다. 한 번의 창 프레임 표본이며 CPU·GPU·화면 제출과 OS 변동을 포함한다. GPU 단독 비용이나 장기 메모리 누수 측정으로 해석하지 않는다. 재질 공유 수는 모든 조건에서 4였고 오프라인 측정 중 표시 개체의 추가 생성·제거는 0이었다. 온라인 표본은 초기 115개체, FPS 938.16·p50 0.932ms·p95 2.204ms였다.

### 적용 결정

현재 상한과 32명 검사 범위에서는 tick 계산이 20ms 예산 안에 충분히 들어오므로 **공간 격자는 이번에 도입하지 않는다**. 더 많은 인원·몬스터를 허용할 때 다시 측정한다.

위치 분산은 몬스터 목록 바이트를 약 23.6% 줄였지만 공격 결과 1,003,520B는 그대로였다. 플레이어 이동·공격·피격 이벤트의 기존 필드 전체 공유가 인원 증가에 따라 커지므로 **다음 전송 확장의 우선 적용 대상으로 주변 전송을 선택한다**. 입장·퇴장·현재 상태·공격자의 표시를 같은 관심 범위로 묶어 적용해야 한다. 이번 변경에는 해당 동작 변경이나 채널 추가 구현을 포함하지 않았다.

### 추가 발견: Windows 창 전환 종료와 남은 검사

`final-controls-2001/player.log`에서 한 번의 네이티브 종료를 발견했다. 첫 스택은 `InputManager.OnFocusChanged → EnableOrDisableDevice → ResetDevice → NativeArray<byte> → UnsafeUtility.MemClear`였다. 이어 실행 루프 재진입 오류가 기록됐다. 종료를 통과 결과로 처리하지 않는다.

Windows Player에서 포커스 콜백의 장치 초기화를 피하고 일반 Update에서 키보드·마우스 초기화/동기화를 수행하도록 보완했다. 복귀 시 두 프레임 동안 조작을 차단하고 UI 입력 모듈과 개별 UI 요청도 배경 입력을 거절한다. 공식 [Input System 포커스 정책](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.17/api/UnityEngine.InputSystem.InputSettings.BackgroundBehavior.html)은 IgnoreFocus가 UI 모듈의 기본 포커스 검사도 끈다고 명시하므로 별도의 UI 차단을 함께 적용했다.

이 보완을 포함한 Unity 빌드는 성공했다. 그러나 `focus-fixed-*` 두 실행 파일의 실제 창 전환 재검증을 시작할 때 사용자가 물리 Escape로 컴퓨터 조작을 중지했다. **새 포커스 보완의 실제 반복 전환·드래그·새 입력 재검증은 아직 완료하지 않았다.** 근본 Unity 오류가 해결됐다고 단정하지 않는다. 기존 UI·DB·부하의 통과 결과와 이 미완료 검사를 구분한다.

검사 종료 정리도 아직 남아 있다. 기존 DB는 실행 중이며 검사 캐릭터의 최대 HP 50,000, 부하용 load 계정과 이번 서버 세션을 유지한 상태다. 재개 시 실제 창 재검증 후 테스트 HP·부하 계정·검사 프로세스를 정리한다. 원본 씬·설정의 빌드 재직렬화 변경은 복원했다.

기본 검사: `RunFieldFeatures.ps1`. 실제 DB 트랜잭션: `InventoryDatabase.exe`. 기존 DB 조작 환경: `FieldValidationSession.ps1`, `FieldValidationDatabase.ps1`. 서버 부하: `RunFieldLoadExisting.ps1 -UseExistingTestDatabase`. Unity 표시: `RunFieldRenderExisting.ps1`.
