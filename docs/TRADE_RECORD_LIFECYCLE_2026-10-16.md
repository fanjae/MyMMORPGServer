# 거래 기록 보관과 저장 형식 이관

## 현재 보장

005_trade.sql의 character_trade_records는 거래 번호, 두 캐릭터 ID, request_payload, committed_at을 저장한다. 현재 payload는 pack(1)의 TradeCommitRequest 250바이트다. 두 캐릭터의 인벤토리·메소·장비 소유권과 기록을 같은 트랜잭션에서 커밋한다. 동일 번호의 같은 payload는 다시 지급하지 않고 다른 payload는 거절한다.

현재는 자동 삭제하지 않는다. 참가자가 기록을 조회할 때 과거 인벤토리를 되돌리는 것이 아니라 현재 인벤토리와 완료 결과를 전달한다. 장비가 이후 다른 거래로 이동했어도 과거 결과 조회가 그 장비를 다시 지급하지 않는다.

2026-10-16에는 메모리에 남은 완료 거래도 조회 시 DB의 현재 인벤토리를 다시 보내도록 보완했다. 완료 결과와 인벤토리 응답이 함께 유실되면 상태만 Completed로 바꾸는 것으로 복구가 끝나지 않기 때문이다. 현재 다른 거래가 진행 중이면 그 진행 상태를 우선해 과거 조회가 새 거래를 덮지 않도록 처리한다.

## 보관 정책 제안

현 테스트 단계에서는 무기한 보관을 유지한다. 아래 운영 값은 제안이며 이번에 삭제 작업을 추가하지 않는다.

| 데이터 | 운영 제안 | 이유 |
|---|---|---|
| 전체 제안 내역 | 90일 기본값, 운영 요구에 따라 조정 | 고객 문의·장애 조사·상세 교환 내역 |
| 중복 방지 요약 | 거래 ID 재사용 가능성이 없는 별도 보장이 마련될 때까지 유지 | 오래된 같은 ID를 새로운 교환으로 처리하지 않음 |
| 진행 중·결과 불명확 거래 | 시간만으로 삭제하지 않음 | 완료/실패 여부를 먼저 확정해야 함 |
| 현재 인벤토리 | 기록 보관과 별도로 현재 상태 유지 | 과거 응답을 복구해도 과거 아이템을 다시 주지 않음 |

전체 기록을 지울 때는 transaction_id, 참가자 ID, payload_format_version, 요청 해시, committed_at을 남기는 compact receipt로 원자적으로 옮긴다. 전체 기록 삭제와 요약 저장 사이에 빈틈을 만들지 않는다. 재시도 경로는 전체 기록과 요약을 모두 확인한 후에만 새 교환을 허용한다.

요약에 같은 번호·같은 형식·같은 요청 해시가 있으면 이미 완료된 결과를 반환한다. 다른 내용이면 Invalid다. 상세 제안이 없어도 참가자와 완료 사실을 확인하고 현재 인벤토리를 조회할 수 있어야 한다. 해시만 저장한 뒤 상세 payload를 다시 적용해서 복원하지 않는다.

계정/캐릭터 삭제 때 기록을 연쇄 삭제하는 현재 외래 키와 장기 중복 방지 정책은 별도 조정이 필요하다. 거래 ID·캐릭터 ID의 재사용 금지와 백업 복원 절차를 함께 정한다. 이 조정 없이 오래된 기록을 일괄 삭제하지 않는다.

## 형식 버전의 분리

네트워크 protocol version과 영수증 payload format version은 분리한다. 네트워크가 다음 버전으로 바뀌어도 이미 저장된 format 1의 해석을 유지한다.

다음 마이그레이션은 기존 행에 payload_format_version=1을 추가하고 새 writer를 활성화하기 전에 새 reader를 배포한다. format 1 reader는 고정 길이 250바이트와 필드 범위를 검증한다. 현재 레이아웃의 크기 고정은 static_assert로 확인하지만 향후 가변 장비/슬롯 배열까지 C++ struct의 메모리 그대로 저장하지 않는다.

format 2는 정해진 little-endian 인코딩, 헤더의 형식 버전·길이, 참가자, 제안 개수, 아이템·인스턴스·수량·메소를 명시한다. 요청 해시는 해당 버전의 정규화된 인코딩에 대해 계산한다. 사용하지 않는 배열 여백이나 컴파일러 패딩을 해시 기준에 포함하지 않는다. 버전이 다른 payload끼리 raw byte 비교를 하지 않는다.

## 배포와 이관 순서

1. 기존 250바이트 기록을 읽는 format 1 reader와 새 reader를 함께 배포한다.
2. DB에 형식 버전·요약 기록 저장 구조를 추가하고 기존 행의 기본값을 1로 둔다.
3. 기존 기록의 수·참가자·거래 번호·해석 가능한 제안 수를 읽기 전용 검사한다.
4. 새 writer를 활성화하고 새 기록만 format 2로 저장한다. 이전 기록을 즉시 덮어쓰지 않는다.
5. 이관이 필요하면 제한된 묶음으로 읽기 → 검증 → 새 형식 저장을 트랜잭션에서 수행한다. 원본 해시와 이관 결과를 비교한다.
6. 재접속 조회·중복 요청·장비 소유자 변경 이후 조회·동시 이관을 검사한다.
7. 삭제/요약 전환은 별도 운영 작업으로 실행하고 실패 시 해당 묶음을 롤백한다.

알 수 없는 형식은 거래를 재실행하거나 단순 NoRecord로 처리하지 않는다. 기록 존재·참가자·완료 시각은 별도 열에서 확인한다. 완료 사실을 증명할 수 있는 경우 현재 인벤토리를 복구하고 상세 내역만 해석 불가로 표시하는 프로토콜을 마련한다. 기록 자체가 손상됐다면 복구 대기로 남기고 운영 조사 대상으로 분리한다.

## 필수 검사

- format 1 기록은 새 서버에서도 동일 참가자의 Completed 조회가 가능해야 한다.
- 다른 참가자의 조회는 기록 내용을 노출하지 않아야 한다.
- 같은 ID에 다른 제안·다른 버전의 요청이 들어와도 다시 지급하지 않아야 한다.
- 상세 기록을 요약으로 바꾸는 중 동시 재시도가 들어와도 한 번만 적용돼야 한다.
- 장비가 다른 소유자에게 이동한 뒤 과거 거래 조회가 현재 소유권을 바꾸지 않아야 한다.
- 손상·잘린 payload·지원하지 않는 형식은 성공적인 신규 거래로 해석하지 않아야 한다.
- 보관 작업은 진행 중/결과 불명확 거래를 삭제하지 않아야 한다.
- 백업 복원 후 과거 거래 ID가 재사용되지 않는지 확인해야 한다.
