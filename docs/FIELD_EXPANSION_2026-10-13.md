# 2026-10-13 전투·장비·드롭 및 복구 보완

현재 3D game protocol은 **11**이다. 서버와 3D 클라이언트를 함께 다시 빌드한다. 기존 2D protocol 6과 Login protocol 2는 유지한다. 같은 PC의 임시 MySQL·LoginServer·GameServer·두 Unity Player에서 검사하며 서로 다른 PC 검사는 수행하지 않는다.

## 구현 범위

- 몬스터는 살아 있는 플레이어를 6m 안에서 탐지·추적하고 약 1.2m 거리에서 1.5초마다 10 피해를 준다. 벽에 가려진 대상은 공격하지 않는다.
- 서버가 HP 감소를 확정한 뒤 하단 HP/MP 게이지와 같은 필드의 피격 표시를 갱신한다. HP 0에서는 이동·공격·물약 사용을 막고 3초 후 ESC 메뉴에서 시작 위치로 부활한다.
- 무기·모자는 고유 장비 번호를 보존하며 착용·해제·교환한다. 목검은 공격 피해 +5, 모자는 받는 피해 -2다. 빈 슬롯·소유권·변경 번호를 서버와 DB에서 검사한다.
- 몬스터 사망 시 빨간 물약 한 개를 생성한다. 드롭 유효 시간은 60초, 획득 거리는 2m, 필드당 최대 드롭 수는 64다. 두 캐릭터가 동시에 획득해도 한 번만 지급한다.
- 로그인·캐릭터 선택·채팅·인벤토리·필드 이동·ESC 메뉴·게임 종료는 SampleScene의 Canvas UI를 사용한다. 사망 중에도 I 키와 INVENTORY 버튼으로 인벤토리를 열 수 있다. OnGUI는 키 이벤트 보완 및 명시적인 입력 기록에만 남아 있으며 화면 UI를 그리지 않는다.

## DB 실패 후 전투 복구

피격마다 서버가 고유 처리 번호를 만들고 `field_combat_mutations`의 기록과 HP·revision 변경을 같은 트랜잭션으로 확정한다. 같은 번호의 재시도는 저장된 HP를 읽고 피해를 다시 적용하지 않는다. 같은 번호에 다른 소유자나 피해량을 보내면 거절한다.

피격 SQL 실패 또는 5초 응답 제한을 넘으면 해당 캐릭터의 전투를 중단한다. 이동·공격·획득·맵 이동 및 신규 인벤토리 변경을 막고 클라이언트와 상대 화면에 중단 상태·확정 위치를 알린다. 기존 피격은 같은 번호로 1·2·4·8초 간격으로 재시도한다. 성공하면 전체 저장 상태와 위치를 맞춘 뒤 전투를 재개한다. 중단 중 누른 키와 대기 공격은 재개 후 재사용하지 않는다.

물약과 피격은 캐릭터 행 잠금 및 같은 DB 작업 큐로 순서대로 확정한다. 결과가 불명확한 물약 사용은 재실행하지 않고 재조회한다. 장애가 10분 지속되면 연결을 종료하고 저장 상태로 재접속하게 한다. 아직 확정하지 못한 대기 피격은 서버 메모리에 있으므로 프로세스 종료·연결 종료까지 영속 재처리를 보장하지 않는다. 이미 커밋한 피해는 DB에 남는다.

## 획득 결과 복구와 기록 정리

획득 요청과 성공 응답 사이에 연결이 끊겨도 지급 요청을 다시 보내지 않는다. 클라이언트는 미확정 드롭 번호를 서버 주소·로그인 포트·캐릭터별로 PlayerPrefs에 보관하고 재접속에서 결과 조회만 수행한다.

opcode 44는 인증된 캐릭터의 획득 기록을 조회한다. 본인이 획득한 경우 Success, 다른 캐릭터가 획득한 경우 AlreadyTaken, 보관된 기록이 없는 경우 NoRecord를 반환하고 현재 인벤토리도 보낸다. NoRecord를 과거에 절대 획득하지 않았다는 뜻으로 표시하지 않는다. 조회는 슬롯·수량·revision을 변경하지 않는다.

응답이 없으면 5초 후 결과를 조회하고 최대 3회 재시도한다. Busy·StorageError는 미확정 상태를 유지한다. LOOT 버튼 또는 Z로 조회를 다시 시작할 수 있으며 신규 획득은 이전 결과를 확인한 뒤 진행한다. 상태 조회도 연결당 진행 작업 1개와 100ms 간격을 적용한다.

획득·피격 기록은 30일 보관한다. 일반 인벤토리 요청 또는 피격·획득·부활 처리가 커밋될 때 최대 5분에 한 번씩 테이블당 500행까지 오래된 기록을 정리한다. 조용한 서버에서는 별도 정리 작업이 실행되지 않는다. 드롭 자체는 메모리에 있으며 서버 재시작 후 복원하지 않는다. 기록 정리 실패는 이미 성공한 지급·피격을 실패로 바꾸지 않는다.

## 주변 전송과 목록 분할

- 몬스터가 32마리 이하인 필드는 기존 샘플의 전체 공유 표시를 유지한다. 32마리를 초과하면 각 플레이어의 XZ 반경 16m 안의 몬스터만 보낸다.
- 몬스터 목록을 32개씩 분할한다. 조각 하나는 헤더 포함 최대 1,024바이트이며 같은 mapId·generation·tick의 part/parts/total 정보를 갖는다. 빈 주변 목록도 한 조각으로 전송한다.
- Unity는 모든 조각을 모은 뒤 한 번에 목록을 교체한다. 다른 tick의 조각을 합치거나 부분 목록을 전체 목록으로 취급하지 않는다. 오래된 tick, 잘못된 조각 수, 중복 몬스터 ID를 거절한다.
- 공통 레코드와 해시는 tick마다 한 번 계산하고 같은 주변 목록의 분할 패킷을 수신자끼리 재사용한다. 이동 상태는 최대 200ms 주기, 동일 상태는 1초 확인 주기를 사용한다.
- 드롭도 반경 16m 안의 목록만 표시한다. 생성·획득·만료 및 플레이어의 주변 목록 진입·이탈에서 바뀐 목록만 전송한다. 수신자별 변경 번호를 사용한다.

이번 주변 제한은 몬스터·드롭 목록에 적용한다. 플레이어의 입장·이동·채팅·공격 이벤트는 기존 필드 공유 범위다. 몬스터 최대 128마리와 드롭 최대 64개는 유지하며, 공간 격자·몬스터 tick 병렬화·송신 우선순위 큐는 추가하지 않았다. 목록 분할로 개별 패킷은 줄지만 패킷 수와 분할 헤더는 늘어난다.

## 기존 DB 적용

기존 DB에는 002 → 003 → 004 순서로 적용한다. 새 볼륨은 초기화 SQL을 파일 순서로 실행하지만 기존 Docker 볼륨에는 새 SQL이 자동 적용되지 않는다. [INVENTORY_DATABASE.md](INVENTORY_DATABASE.md)에 적용 명령과 확인할 테이블을 정리했다. 사용자 DB를 자동으로 수정하지 않고 임시 DB에서만 검증한다.

## 검사 결과

- 서버 규칙·네트워크 검사: 공격 거리·방향·벽·중복 입력·사망·재생성, 장비 소유권, 주변 목록 진입·이탈, 분할 크기·총 개수, 같은 드롭 목록의 반복 전송 생략 통과.
- C# 클라이언트 검사 18개 묶음: 분할 목록의 원자적 교체·순서 변경·이전 tick·중복 ID, 획득 조회의 재시도 제한·재접속·미확정 오류 보존 및 기존 이동·입력·인벤토리 규칙 통과.
- 실제 임시 MySQL 검사 16개 묶음: 장비 트랜잭션, 동시 획득, 피격 재시도 중복 차단, 강제 SQL 실패의 처리 기록·HP 동시 롤백, 획득 소유자 조회, 오래된 기록 정리 통과.
- 실제 두 Unity Player: protocol 11 인증·입장·상대 점프/착지·인벤토리·공유 몬스터·렌더링 통과. 서버 재시작 전후 DB의 HP·MP·revision이 정확히 일치했다.
- 실제 서버 획득 결과 조회: 본인/다른 캐릭터/기록 없음 구분 및 조회 후 수량 불변 통과. 실제 SQL 제약 오류 뒤 전투 중단·복구 중 맵 이동 거절·피해 한 번 적용·동일 입장 번호에서 재개 통과.

최종 전체 통합 검사 로그는 `artifacts/full-3d-203f7df7b2d842498465ae09dd0e5f20/`에 보관했다. `field-expansion.log`, `field-recovery.out`, `inventory-database.log`, 두 Player의 `Logs/3d-smoke-full-*.result` 및 `integration.result`를 확인할 수 있다. 서버 규칙·주변 전송 로그는 `artifacts/field-recovery-server-final.log`, 0/80±35/150±60ms TCP 로그는 `artifacts/field-recovery-tcp-tests.log`다. 검사 중 발생한 이전 실패 로그도 각 별도 실행 디렉터리에 남겨 두었다.

자동 검사는 실제 J·Ctrl·ATTACK·드래그를 사람이 조작한 결과와 구분한다. 사람에 의한 반복 입력·드래그 체감 및 서로 다른 PC 검사를 완료했다고 기록하지 않는다. Unity 오프라인 부하 검사의 프레임 시간은 전체 프레임 시간이며 GPU 단독 비용은 아니다.

## 채널 작업 대기

기존에 구현한 한 GameServer 내부의 3개 논리 채널과 ESC 메뉴는 보존한다. 사용자 요청에 따라 채널 수·정원·점검 상태·마지막 채널 저장·서버 간 접속 이전 등의 추가 구현은 대기한다. 이번 보완에서 채널 관리 구조는 확장하지 않았다.
