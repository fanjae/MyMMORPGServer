# 플레이어·전투 주변 전송의 다음 구현 계약

이 문서는 구현 범위를 확정하기 위한 설계다. 현재 런타임은 플레이어·이동·공격을 같은 채널·맵 전체에 전송한다. 몬스터·드롭의 기존 주변 목록과 이 설계의 플레이어 관심 목록을 구분한다. 신규 채널은 추가하지 않는다.

## 첫 적용 기준

| 항목 | 제안 기준 |
|---|---|
| 공간 | 같은 Map 인스턴스, XZ 평면 거리. 채널·맵이 다르면 후보에서 제외 |
| 진입 | 거리 16m 이하. 서버 단위 320 이하, 제곱 거리 비교 |
| 유지/이탈 | 이미 보이는 대상은 18m까지 유지하고 18m 초과에서 이탈 |
| 높이 | 첫 단계의 표시 관심 범위에서는 별도 높이 필터를 두지 않음. 공격의 높이 차이 1.5m 판정은 그대로 유지 |
| 자기 상태 | 자기 인벤토리·피격·복구·거래 결과는 관심 범위와 무관하게 전달 |
| 갱신 | 20ms Map tick의 상태 갱신 후 계산. 행동·전투 표시 전송은 같은 tick의 관심 목록 사용 |
| 후보 검색 | 기존 플레이어 목록의 거리 검색부터 적용. 공간 격자는 별도 측정 후 결정 |

16/18m는 다음 구현의 시작값이다. 몬스터 목록은 32마리 초과 필드에서 현재 16m 단일 반경을 사용하며 드롭도 16m다. 첫 단계에서 몬스터·드롭 반경을 조용히 바꾸지 않는다. 공격 3m·획득 2m·높이 1.5m는 표시 범위와 별도의 게임 규칙이다.

## 순서와 대기 데이터

한 tick은 입력 적용 → 월드·DB 확정 상태 반영 → 관심 목록 계산 → 이탈 정리/진입 기준 상태 → 이동/공격/피격 전송 순서로 처리한다. 현재 즉시 공격 방송은 이 전송 단계에 모으는 변경이 필요하며 최대 한 tick의 표시 지연을 명시한다. 자기 DB 결과 응답은 해당 표시 대기를 기다리지 않는다.

- 진입: 캐릭터 ID·이름·현재 이동 기준 상태·생존/HP·전투 중단·공개 장비 외형을 먼저 전달한다. 다른 플레이어의 인벤토리 목록은 공개하지 않는다.
- 이후 행동: 기준 상태보다 뒤의 순번만 전달한다. 진입 전에 받은 오래된 이동을 새 객체에 재생하지 않는다.
- 이탈: PlayerLeave와 함께 수신자별 대기 이동·공격 표시를 제거한다. 다시 진입하면 새 기준 상태부터 시작한다.
- 서버 내부 대기 레코드에는 수신자 Map generation과 대상별 관심 세대를 저장한다. 이탈·재진입으로 세대가 바뀐 레코드는 전송 직전에 버린다.
- 현재 TCP의 한 연결 안에서 진입·행동·이탈 순서를 보장한다. 이미 전송한 과거 패킷은 이탈보다 먼저 도착한다. 향후 다른 전송 경로를 도입할 때는 관심 세대의 wire 필드 필요성을 다시 검토한다.
- 맵 이동·채널 이동·부활에서는 기존 generation 규칙으로 모든 관심 목록·조립 중 목록·대기 이벤트를 초기화한다.

현재 PlayerEnterMap·MovementState3D·Vitals3D를 재사용할 부분과 장비 외형 초기 상태를 추가할 부분을 나눈다. 진입 상태·선택적 공격 정보의 패킷 정의가 확정된 뒤 3D 프로토콜을 올린다. version 12 수신자에게 새 가변 레코드를 전송하지 않는다.

첫 진입은 이름·이동·HP·외형을 합친 VisiblePlayerState 한 레코드로 전달하는 방안을 우선한다. mapId/generation, characterId, 제한된 UTF-8 이름, source latestClientTick, 기존 84바이트 이동 행동 기준 상태, HP/최대 HP, 전투 중단 여부, 카탈로그 버전, 부위/공개 아이템 ID 목록을 포함한다. 개인 장비 인스턴스 ID는 포함하지 않는다. 크기·이름 길이·부위 수를 먼저 검증한 뒤 객체를 보이게 한다.

기존 여러 패킷을 재사용한다면 새 객체는 필수 기준 상태가 모두 모일 때까지 숨겨 둔다. 한 프레임의 256패킷 처리 한도에서 이름만 받은 객체가 원점에 먼저 나타나지 않도록 한다. 관심 목록 대량 진입은 패킷당 레코드 수와 연결별 송신 바이트 예산으로 나누되 각 캐릭터의 기준 상태를 중간에 잘라 적용하지 않는다.

## 공격과 피격의 전달

현재 기본 공격 대상은 몬스터이고 플레이어 피격은 몬스터 공격에 따른다. 이 설계가 PvP 구현을 추가하는 것은 아니다.

| 공격자 플레이어 | 대상 몬스터 | 수신 내용 |
|---|---|---|
| 보임 | 보임 | 같은 사건 번호의 휘두르기·대상 피해·확정 HP |
| 보임 | 안 보임 | 휘두르기 표시만 전달. 숨은 대상의 ID·좌표·HP를 새로 노출하지 않음 |
| 안 보임 | 보임 | 대상의 피해·확정 HP만 전달. 공격자 객체를 강제 생성하지 않으며 숨은 공격자 좌표도 보내지 않음 |
| 안 보임 | 안 보임 | 관전자에게 표시 이벤트를 보내지 않음 |
| 자기 피격 | 무관 | 자신의 확정 HP·피해·사망·복구 상태를 항상 전달 |

현 BasicAttackEvent의 Hit 결과는 대상 ID·HP가 필수이므로 필드를 0으로 지워 휘두르기 전용으로 사용하면 안 된다. 다음 프로토콜에서 swing-only와 target-hit 표시를 구분하거나 정보 존재 플래그를 정의한다. 피해 적용은 DB 확정 한 번이며 수신자마다 표시 레코드를 나누어도 재적용하지 않는다.

## 거래·채팅과 이름 목록

거래의 현재 규칙인 같은 채널·맵을 유지한다. 관심 목록에서 빠졌다는 이유만으로 확정 중 거래를 취소하지 않는다. 거래 결과는 참가자에게 직접 보낸다. 이름만 필요한 거래 상대 목록·일반 채팅의 이름 해석은 위치가 포함된 플레이어 표시 목록과 분리하는 방안을 적용 범위에 포함한다. 전체 맵 거래를 유지하면서 근처 표시 목록만으로 상대 선택을 제한하는 변경을 암묵적으로 넣지 않는다.

## 표시 객체 재사용

서버의 목록 진입·이탈과 클라이언트 Instantiate/Destroy 횟수는 다른 측정이다. 패킷 검사에서 같은 ID가 돌아왔다는 결과를 객체 풀이 동작했다는 결과로 쓰지 않는다.

풀 반환 시 ID·revision·이동 시간선·HP/사망 표시·공격 표시·피해 숫자·숨김 타이머·이벤트 연결을 정리한다. 획득 중 드롭의 로컬 잠금과 설명도 초기화한다. 대여 시 새 ID와 기준 상태를 적용한 뒤 보이게 한다. Map generation 변경은 현재 대여 목록을 모두 반환하고 진행 중 효과를 취소한다.

이 정리는 표시 컴포넌트의 상태에만 적용한다. 캐릭터의 미확정 획득/거래 번호와 저장된 복구 상태는 목록 이탈이나 풀 반환 때문에 지우지 않는다. 드롭 객체가 보이지 않아도 서버 결과 조회는 계속할 수 있어야 한다.

풀의 총 보관 개수는 현재 프로토콜 개체 상한에 맞춰 제한하고 초과 반환은 제거한다. 재질 공유를 유지한다. 계측은 새 생성·대여·반환·제거·활성 수·보관 수·프레임 시간·할당량을 각각 기록한다. 이번에는 풀을 런타임에 구현하지 않는다.

## 검증 행렬

1. 16m 안 진입 시 기준 상태가 이동보다 먼저 도착하고 동일 ID가 한 번만 생성되는지 검사한다.
2. 16~18m 왕복에서는 기존 대상이 유지되고 18m 초과 후에는 한 번 이탈하는지 검사한다.
3. 정확한 16m/18m와 양옆의 최소 좌표 단위를 비교한다.
4. 빠른 이탈·재진입에서 이전 관심 세대의 이동·공격이 새 객체에 적용되지 않는지 검사한다.
5. 위 공격자/대상 가시성 네 조합의 패킷 필드와 피해 단일 적용을 검사한다.
6. 자기 피격·사망·부활·DB 복구는 범위 밖 공격자 여부와 무관하게 수신하는지 검사한다.
7. 맵·채널 이동 때 이전 관심 목록과 부분 조립 상태가 모두 사라지는지 검사한다.
8. 늦은 입장에서 현재 생존·장비·전투 중단 상태를 먼저 받는지 검사한다.
9. 거래·일반 채팅·귓속말 규칙이 표시 필터 변경으로 달라지지 않는지 검사한다.
10. 몬스터·드롭 경계 왕복에서 같은 ID가 복귀하고 풀의 이전 효과가 남지 않는지 검사한다.
11. 느린 수신자 한 명의 대기 증가·종료가 다른 수신자를 막지 않는지 검사한다.
12. 동일한 밀집/분산 배치로 적용 전후의 수신 바이트·중계 대기·tick 시간을 비교한다.

## 128명 측정에서 확인한 별도 한계

2026-10-16 실제 서버에서 128명이 0.6초 간격으로 공격/이동 확인을 보내자 수신자별 이동 대기 256개 상한에 도달해 연결들이 종료됐다. 직전에는 수신자별 244개·최대 중계 대기 약 1.2초였고 마지막 구간 queueOverflows=128이었다. 이 결과를 통과로 기록하지 않는다.

한 3D 중계 패킷은 최대 42개 행동이며 현재 수신자별 전송 주기는 200ms다. 이론상 약 210개/초의 레코드 처리량에 게임 루프 주기와 송신 변동이 더해진다. 반면 128명×약 1/0.6초는 약 213개/초이므로 대기가 누적될 수 있다. 측정 tick 계산이 20ms 안이라는 사실만으로 이 중계 한계가 해결되지 않는다.

관심 범위는 분산 배치의 fan-out을 줄이지만 같은 지점에 모두 모이면 효과가 없다. 후속 구현에는 연속 체크포인트의 안전한 병합 또는 논리 송신 주기 안의 분할 패킷/바이트 예산 검토를 포함한다. Jump/Input/Land/Respawn 순서를 버리는 단순 큐 삭제는 허용하지 않는다. 현재 상한 종료 장치는 유지한다. 이 변경은 이번에 적용하지 않았다.

평균 유입량이 처리량 이하이어도 동시 입력의 지연은 남는다. 96개 행동이 한꺼번에 쌓이면 42개씩 세 번 전송해야 하므로 현재 200ms 송신 간격에서 마지막 묶음은 앞선 묶음보다 최소 400ms 늦다. 연결이 유지되는 96명 조건도 표시 품질의 통과 기준으로 대신할 수 없다. 측정의 최대 중계 대기를 상대 표시 버퍼의 최대 400ms와 함께 검토한다.

논리 송신 주기 안에서 여러 패킷으로 나누는 방안을 택하면 현재 물리 패킷 초당 5회 규칙은 그대로라고 할 수 없다. 발신 클라이언트의 5회 제한과 서버 수신자별 전송 예산을 분리하고, 후자의 패킷/바이트 상한을 별도로 확정해야 한다. 물리 패킷 5회를 반드시 유지한다면 주변 대상 축소와 레코드 축약 형식부터 설계한다. 이 선택은 프로토콜과 계측 기준을 함께 바꾸는 후속 범위다.

96명 2시간 측정 결과는 별도 검증 문서에 기록한다. 공간 격자는 후보 검색 계산 비용을 줄이는 도구이며, 모두가 서로를 보는 밀집 구간의 전송량 자체를 줄이지는 못한다.

현재의 우선순위는 플레이어 관심 목록과 중계 지연/처리량 계약을 다음 프로토콜 묶음으로 구현하고, 공간 격자의 즉시 도입은 보류하는 것이다. 128명 한계는 후보 검색 CPU보다 중계 큐 포화로 재현됐다. 격자 판단은 다인원 실제 이동·분산 배치에서 후보 검색 구간의 시간과 후보 수를 따로 계측한 뒤 다시 한다. 이번의 고정 위치 부하와 공유 PC의 tick 최대값만으로 검색 자료구조의 효과를 수치화하지 않는다.

최종 바이너리의 각 120초 실제 표본에서 96명 밀집/네 위치 분산의 몬스터 수신량은 약 166.98/131.30MB였고, 중계 최대 대기는 642/644ms였다. 기존 몬스터 필터의 수신량 차이는 확인했지만 플레이어 중계 지연은 남았다. 1KiB/초 수신 제한을 건 한 연결이 TCP 송신 한도로 종료된 뒤에도 다른 95명은 표본 끝까지 정상 유지됐다. 수치·완전한 범위는 [검증 결과](HEADLESS_FIELD_VALIDATION_2026-10-16.md)에 기록한다. 이는 새 관심 목록이나 격자를 적용한 전후 비교는 아니다.
